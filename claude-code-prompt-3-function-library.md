# Prompt 3 for Claude Code: reusable function library for 26.3 datapacks

Run from `C:\Users\lrafy\mc-datapack-tools`. Read `CLAUDE.md` first and obey it (verify from `generated/` and `knowledge/`, lint after edits, run server tests, log lessons).

## Goal
Future datapack projects should CALL tested, parameterized function files instead of re-writing the same command sequences. Build a reusable library datapack plus an index so Claude finds and reuses functions before writing new ones.

## Step 1: Research (verify, do not recall)
- How function macros work in 26.3: `$` lines, `function ... with storage|entity|block`, argument escaping and quoting rules, what types macro arguments can hold, error behavior for missing keys, limits, performance cost versus plain functions. Prove each rule with a server test; record in `knowledge/function-macros.md` with the test as evidence.
- Argument-passing patterns: macro args via storage, scoreboard-based args for hot paths (no macro cost), `return` values and `return run`, recursion/loop patterns and their limits, scheduling patterns (`schedule function`, `tick`-based timers), execution-context rules (`as`/`at` inheritance into called functions).
- Existing community conventions for library datapacks (namespacing, versioning, load order, dependency on a shared pack); note what is useful, ignoring anything unverifiable.

## Step 2: Design principles
- Flexible and data-driven; no project-specific values hard-coded. Everything configurable comes in as arguments or a documented config in `data storage`.
- Namespace `mcdp_lib` (configurable by the build tool if a project wants its own prefix). Internal helpers under `mcdp_lib:_internal/`; public API under categorized folders.
- Prefer scoreboard/storage fast paths for per-tick code; use macros for rarely-called setup code. Document the choice per function.
- Each public function has a header comment: purpose, inputs, outputs, side effects, execution context required, example call.
- Library is a normal datapack at `library/mcdp_lib/` that passes lint with 0 errors and ships with tests.

## Step 3: Build the library (each function tested on the real server)
Cover at least these categories, adding more when your research shows common needs:
- **Scoreboard/data helpers:** create-if-missing objectives, add/set/reset/compare, copy score to storage and back, clamp, min/max, safe divide, per-player and global counters.
- **Timers and cooldowns:** start/tick/expire per entity and global, callback function on expiry (macro), pause/resume.
- **Randomness:** random int in range, weighted pick from a storage list, shuffle, pick N unique.
- **Lists and storage:** push/pop/queue, find, remove by index, iterate with a callback function.
- **Players and teams:** count players matching a tag/team, random player, tag/untag helpers, team setup, save and restore inventory/gamemode/position.
- **Messaging:** broadcast/message with a text component stored in data, title/actionbar helpers, simple formatted countdowns.
- **Items:** give/clear items by component data from storage, kits from storage, custom named items with `custom_data` ids.
- **World helpers:** teleport to stored coordinates, fill/clone/place region by arguments, tick-budgeted region fills (spread across ticks), safe-spawn lookup.
- **Rule application:** apply a rules struct (gamemode, pvp-related effects, block-break restriction via the verified mechanism, keep-inventory-like behavior) from storage; revert.
- **Flow control:** generic state machine (state in storage, transitions as function ids), wait-N-ticks-then-call helper, repeat-N-times helper with caps.
- **Debug:** toggleable logging to chat/log with levels.

## Step 4: Index so it gets reused
- `library/INDEX.md`: one line per public function (path, signature, one-line purpose), generated by a script `tools/gen_library_index.py` that reads the header comments. Fail the script when a public function lacks a header.
- Extend `tools/lint_datapack.py` so projects using the library get arguments checked where feasible (at least that called library functions exist).
- `tools/new_project.py <name> <path>`: copies `template-datapack/` plus the library into a new project with a chosen namespace, ready to lint and test.
- Update `CLAUDE.md` (keep under 200 lines) with a rule: before writing a new function, search `library/INDEX.md`; if you write something reusable that is missing, add it to the library with tests. Create a skill `function-library` (if writing to `.claude/skills` is blocked, put it in `install/skills/function-library/SKILL.md` and say so in your report).

- A test runner target that runs the whole library suite in one command.
- Show real output for: the full suite passing, a deliberately broken library function failing, the index generator output, and `new_project.py` producing a pack that lints and passes its tests.
